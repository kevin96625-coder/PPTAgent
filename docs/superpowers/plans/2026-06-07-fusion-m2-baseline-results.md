## 三个会改写 M2 的发现

### 1. 分数偏低(7.49 vs README 8.3–8.5)的三因 —— 不是退化,是测量口径
- **缺精确 style YAML**:本次 prompt 只给了泛化风格说明,生产管线会注入该 style 的完整 token。token 缺失会让 reviewer 对配色/字体合规性扣分。
- **无 slide-role 上下文**:reviewer 不知道 **slide-01 是封面、slide-14 是尾页**(各仅 1 卡/2 单元),按"信息密度/布局平衡"硬评 → 6.0 / 5.5,把均分拉低。生产管线的 holistic 审查知道页角色。
- **逐页孤立评**:本基线没跑 holistic(跨页一致性)那一层,而 README 分含整体协调。
→ **M2 启示**:reviewer 必须拿到 **style token + slide-role(cover/content/end)**,否则封面/尾页被系统性低估。这是 M2 质量门控的一个具体改进点,不是把目标分往上顶。

### 2. "通过率"必须区分两种语义
- 本基线 57% = **成品复审通过率**(已交付页里多少能过新审查)。
- v3 目标"一次通过率 ≥60%"指的是**生成期首轮通过率**(每页第一次设计就过、不进 fix loop)。
- 两者**不可混用**。首轮通过率 + 平均修复轮次**只能靠一次带埋点的 `/ppt` 生成**取得(保留 `review-manifest.json` 的 `fix_rounds` 字段)。

### 3. 密度定义已可操作
"信息单元 = Bento 卡片(rounded-rect 面板)+ 标题块",超标=>7 单元/页。这套定义下成品 deck 超标率 7%、均 5.2 单元/页,落在 v3"≤10% 超标"目标内。**建议把这个定义写进 M2 的 `planning_validator`**,作为密度门控的判定规则。

## 仍缺的一块 & 怎么补
**首轮通过率 + 修复轮次**需要一次**真实 `/ppt` 生成**并保留 `review-manifest.json`。该生成依赖插件专属 agent(research/content/slide/review-core)+ 3 个交互 Hard Stop,**只能在加载了 ppt-agent 插件的 Claude Code 会话里由用户驱动**(本会话的通用 agent 跑不了那套编排)。
→ **建议**:把"带埋点基线生成"作为 M2 计划的**第一个任务**(由用户在插件会话里跑一次标准 12 页,产物回灌)。Gemini 鉴权已就绪,不再是阻塞。
